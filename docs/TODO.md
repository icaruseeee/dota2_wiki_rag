## P0 — 可用性

不做这些，前面所有工作都只是一个能跑通的 demo。

- [ ] **P0-1 答案级评测集**
  - 为什么：现在只测了检索，8 条问答是肉眼看的。换切块、换模型、调 prompt 都无法判断进退。
  - 做什么：30–50 题，带标准答案与允许引用；指标为 faithfulness、answer correctness、citation accuracy。
  - 验收：`npm run eval:answer` 输出三个指标，并进 CI。
  - 估时：1–2 天。

- [ ] **P0-2 最小 HTTP 服务**
  - 为什么：68s 的同步响应没人愿意等；现在只有 CLI。
  - 做什么：`POST /ask`（SSE 流式）、`GET /health`、请求级 trace（embed / recall / rerank / generate 各段耗时与 token 数）。
  - 验收：首 token < 3s（先流式吐来源），全程可观测。
  - 估时：1–2 天。

- [ ] **P0-3 查询缓存**
  - 为什么：bmb_rag 有精确 hash 缓存，我们每次查询从零算，68s 全付。
  - 做什么：精确 hash 缓存（问题 → 答案 + 来源），TTL 绑定数据版本；语义缓存默认关闭。
  - 验收：重复问题 < 100ms 返回，命中率进 trace。
  - 估时：半天。

## P1 — 检索质量

现有索引就能做，不需要重跑入库。

- [ ] **P1-1 RRF 混合检索**
  - 为什么：`pg_trgm` 索引建了从未使用；q08「林肯法球」向量只排 #14，靠重排救回，本质是词汇问题。语料全是专有名词，字面匹配区分度很高。
  - 做什么：dense top-20 与 trigram top-20 用 RRF 融合，再送重排。
  - 验收：18 题 Hit@1 / MRR 不降；q08 的向量排名前移。
  - 估时：半天。

- [ ] **P1-2 结果多样性（MMR 或每文档上限）**
  - 为什么：实测 top-4 里 28% 的槽位是同一文档的重复，q1/q2/q7 都是 4 块里 3 块来自同一篇，等于只覆盖 2 篇文档。
  - 做什么：先做「每文档最多 N 块」，再评估 MMR。
  - 验收：top-4 去重文档数从 23/32 提升，且 Hit@1 不掉。
  - 估时：半天。

- [ ] **P1-3 按分数阈值截断，替代固定 top-4**
  - 为什么：8 题里几乎每次都有 1 个噪音块混进 top-4（回光返照、决斗、灵动之翼）。
  - 做什么：重排分数低于阈值的不入 context，至少保留 2 块。
  - 验收：噪音块占比下降，答案质量不降。
  - 估时：半天。

- [ ] **P1-4 相邻块扩展（parent-doc / 邻居拼接）**
  - 为什么：一篇机制文被切成 10–20 块，命中第 5 块拿不到第 4、6 块。现在是「小块检索 + 小块喂模型」，两头都不占优。
  - 做什么：命中后按 `source_id + chunk_index` 取前后各 1 块，或整篇作为父文档回填。
  - 验收：多跳题（q7 类）答案更完整，context token 不超预算。
  - 估时：1 天。
