## 1. 30 秒、2 分钟和 10 分钟版本

### 1.1 30 秒版本

> 我做了一个本地 Dota 2 中文 wiki RAG。离线把 1,120 个英雄/技能/机制文档实体切成
> 1,718 个检索块，用 Qwen3-Embedding 生成 1,024 维向量，存进 PostgreSQL 和
> pgvector HNSW。在线先召回 20 个候选，可选地用 Qwen3-Reranker 精排，然后在
> 2,400 token 预算内取最多 4 块，交给本地 Qwen3.5-9B 流式回答。18 道检索题上，
> 纯向量 Hit@5 是 94%，加重排后 Hit@1 94%、Hit@5 100%；但重排在 M1 上要 20–50 秒，
> 所以产品默认关闭精排。这个项目最有价值的不是“跑通”，而是把切块、增量入库、
> 评测和延迟取舍都做成了可复现的证据。

### 1.2 2 分钟版本

按以下顺序讲：

1. **问题**：Dota wiki 是事实密集、实体和数字很多的中文知识库，用户会问技能数值、
   归属关系和机制差异。纯 LLM 容易凭记忆答错，也不能给出来源。
2. **离线链路**：结构化导出 → 实体级组装 → 标题感知切块 → 精确 token 校验 →
   Qwen3 embedding → pgvector。
3. **在线链路**：query embedding → 向量 top 20 → 可选 cross-encoder 精排 →
   token 预算取块 → context-only prompt → SSE 流式回答。
4. **关键工程点**：跳转桩转别名、短碎片合并、超限直接失败、内容哈希增量、
   快速/精排双模式。
5. **评测**：检索用 Hit@k/MRR，答案用上下文召回、答案匹配、引用命中、拒答和
   数字支持检查。
6. **取舍**：当前只做 dense，没有 hybrid、query rewrite、MMR、邻居扩展和引用校验；
   这些不是不知道，而是按语料规模、延迟和收益排序后暂缓。

### 1.3 10 分钟版本

把 2 分钟版本展开成：

- 业务与数据规模；
- 为什么不用 fine-tune；
- chunking 的具体算法和失败模式；
- embedding 和 index 选型；
- dense 与 hybrid 的边界；
- reranker 为什么有效、为什么默认关；
- 评测集构造和指标局限；
- 下一步实验优先级。

## 2. 项目定位与问题定义

### 2.1 业务问题

目标不是做通用 Dota 助手，而是回答“wiki 里写了什么”：

- 某个技能的冷却、魔法消耗、施法距离；
- 某个技能属于哪个英雄；
- 两个机制概念有什么区别；
- 某个效果是否会被驱散；
- 资料不足时明确拒答，而不是补常识。

这类问题的特点是：

- **实体密度高**：一个短问题可能包含英雄名、技能名、装备名和机制名。
- **答案短而精确**：通常是一个数字、归属关系或几句机制说明。
- **引用重要**：用户需要能回到 wiki 页面核对。
- **语料有边界**：不能回答实时比赛、版本胜率或未来更新。

### 2.2 为什么用 RAG，而不是 fine-tune

1. wiki 内容会更新，RAG 只需重建索引；fine-tune 需要重新训练和发布。
2. RAG 可以返回来源，fine-tune 很难保证可追溯。
3. 当前数据量只有约 1,100 个实体，检索成本低。
4. 没有足够的高质量问答对做领域微调，而自动评测集也不适合直接当训练集。
5. 语料外问题可以通过检索结果和 prompt 拒答，而不是强迫模型“记住”。

面试时不要说“RAG 一定优于 fine-tune”。更准确的说法是：

> 这个任务的核心矛盾是知识可更新、答案要可追溯，所以优先 RAG；
> fine-tune 更适合固定输出风格、领域语言习惯或特定推理模式。

### 2.3 成功标准

- 检索：相关内容能否进入 top-k；关键实体是否排在前面。
- 上下文：进入 prompt 的块是否真的包含答案。
- 答案：是否只依据资料、数字是否被资料支持、是否标注来源。
- 拒答：语料外问题是否不编造。
- 体验：来源何时出现、首 token 何时出现、总延迟是否可接受。

## 3. 端到端架构

```text
离线：
dota2-wiki.json
  -> chunk.mjs
     -> 结构化字段组装
     -> 实体/标题边界切分
     -> /tokenize 精确计数
  -> chunks.json
  -> ingest.mjs
     -> md5 增量判断
     -> Qwen3-Embedding
     -> wiki_chunks + HNSW

在线：
question
  -> embed
  -> dense top 20
  -> optional rerank
  -> token-budget selection
  -> prompt
  -> Qwen3.5-9B stream
  -> SSE + source cards
```

### 3.1 关键参数

| 参数 | 值 | 理由 |
| --- | --- | --- |
| `RECALL_K` | 20 | 给精排足够候选，同时控制精排成本 |
| `TOP_N` | 4 | 小规模事实问答通常 2–4 块足够 |
| `CONTEXT_BUDGET` | 2,400 | 给 9B 模型留生成空间，避免上下文过长 |
| `MIN_TOKENS` | 60 | 过滤标题+一句话的高相似度碎片 |
| `MAX_TOKENS` | 1,800 | 为 2,048 硬限制留 248 token 余量 |
| `TARGET_TOKENS` | 1,000 | 平衡上下文完整性和检索粒度 |

### 3.2 本地推理栈

- Embedding：Qwen3-Embedding-0.6B-Q8_0，端口 8080。
- Reranker：Qwen3-Reranker-0.6B-Q6_K，端口 8082。
- Generator：Qwen3.5-9B-Q4_K_M，端口 8081。
- 存储：PostgreSQL 18 + pgvector 0.8.7。

这三个模型角色不能混用：

- embedding 模型输出向量；
- reranker 需要 query-document 对，并通过 `/v1/rerank` 打分；
- 生成模型负责自然语言回答。

## 4. 文档解析

### 4.1 本项目实际做了什么

仓库内没有直接抓取 HTML、PDF 或 OCR。当前输入是已经归一化的
`data/dota2-wiki.json`。`chunk.mjs` 做的是“结构化字段 → 检索文本”的组装：

| 来源 | 组装内容 |
| --- | --- |
| 英雄 | 名称、英文名、阵营、主属性、背景、简介、玩法、天赋 |
| 技能 | 名称、归属英雄、施法消耗/冷却/距离、描述、机制说明、数值、神杖/魔晶升级 |
| 机制文 | Markdown 正文、标签、内嵌表单、站内跳转别名 |

因此面试时要区分两个概念：

- **上游文档解析**：把网页 DOM/API 响应变成结构化 JSON。当前仓库不做。
- **下游检索组装**：把结构化字段拼成适合 embedding 的块。`chunk.mjs` 做这个。

### 4.2 为什么不让仓库重新解析原始 HTML

1. 上游导出已经处理了导航、占位符、表格和内嵌表单，重复解析会增加漂移风险。
2. 抓取脚本不在仓库里，重新做 HTML parser 会让项目从“RAG”变成“爬虫工程”。
3. 结构化字段允许我们保留实体边界、外键和来源 URL，比纯文本更可靠。
4. 当前评测和问题都基于这份导出，先把检索链路做扎实更有价值。

### 4.3 如果要从零做解析，面试怎么答

应该描述一条可验证的流水线，而不是只说“用 BeautifulSoup”：

1. 抓取与缓存：保留原始响应、URL、时间戳和版本号，支持断点续跑。
2. 去模板：移除导航、广告、页脚和重复模块。
3. 结构保留：标题层级、列表、表格、代码块、图片说明和链接。
4. 实体关联：把英雄、技能、机制、标签和表单拆成有主键的表。
5. 文本归一化：空格、全角/半角、占位符、HTML 实体和表格转 Markdown。
6. 媒体处理：图片走 OCR/VLM 或至少保留 URL 和 caption。
7. 质量校验：字段覆盖率、外键完整性、重复率、空文档率和超长块比例。
8. 版本化：原始数据、解析结果和索引版本可追溯。

### 4.4 当前解析的缺口

- 图片和流程图没有进入文本索引；项目记录的护甲公式只存在于 PNG。
- 表格和复杂排版主要依赖上游 Markdown，没有布局感知解析。
- 部分上游数据本身有缺陷：
  - `傀儡目标`（hero_id=127）没有技能和传记；
  - 3 个技能中文名被截断到 20 字符；
  - 标签 ID 454、644、1225 被引用但不在标签表内；
  - 水晶室女「冰川护体」的魔晶关系标注不一致；
  - 项目记录中有 148 张内容图片未入库。

这些不是靠“换一个 embedding 模型”就能解决的，属于数据层问题。

## 5. Chunking 策略

### 5.1 本项目采用的策略

不是固定 512 字或 512 token，而是“实体优先、标题感知、token 约束”：

| 类型 | 策略 | 结果 |
| --- | --- | --- |
| 英雄 | 一英雄一块 | 129 块 |
| 技能 | 一技能一块 | 1,040 块 |
| 机制文 | 按 h2–h4 切，合并小片段，再贪心打包 | 549 块 |

机制文的具体过程：

1. 用 Markdown 标题切成语义小节。
2. 不足 150 字符的片段向后合并，避免“标题 + 一句话”污染相似度。
3. 贪心装入约 1,000 token 的块。
4. 单个片段超过 1,800 token 时递归按段落、换行、句子拆分。
5. 最终每块用 embedding 服务的 `/tokenize` 精确计数。
6. 超过 2,048 token 的块直接报错，拒绝写入不完整索引。

每个块前会拼接 header，例如：

```text
技能：毁灭阴影（Shadowraze）
归属英雄：影魔
施法：魔法消耗 90 · 冷却 10 · 施法距离 200
```

这样一个小节即使离开了原页面，也能保留实体和属性上下文。

### 5.2 为什么不用固定窗口

固定窗口把文本当成等长字节流，但在 wiki 里：

- 一个技能的所有数值天然属于同一条知识；
- 一个机制的标题和后续段落有强依赖；
- 固定切分可能把一个技能拆成“冷却”和“描述”两块；
- 也可能把两个无关实体拼进同一块，稀释向量。

对这个语料，实体边界比字符边界更有意义。

### 5.3 为什么目标 1,000、软上限 1,800、硬上限 2,048

- 2,048 是 embedding 服务的硬限制。
- 1,800 留出约 248 token 的余量，避免估算误差。
- 1,000 是检索粒度和上下文完整性的折中：太小会碎片化，太大容易一个向量覆盖多个主题。
- 最终不靠字符估算，而是用服务自己的 tokenizer 复核。

### 5.4 幂等和增量

- `chunk_key = doc_type:source_id:chunk_index`。
- `content_hash = md5(text)`。
- 入库时比较已有哈希，只重算变化块。
- 重切后清理不再存在的 key，避免旧内容残留。

注意：`chunk_key` 稳定不等于切块语义稳定。修改切块逻辑后，仍应重跑评测，
不能只看数据库行数没变。

### 5.5 没有采用的 chunking 变体

- **固定长度 + overlap**：实现简单，但会切断实体边界；本语料不需要靠 overlap 弥补。
- **语义切块（按 embedding 相似度找边界）**：多一次模型调用，当前标题边界已经清晰。
- **parent-child retrieval**：小块检索、大块回填，适合长文和多跳，当前没有做。
- **相邻块扩展**：机制文命中第 5 块时，拿不到第 4、6 块，是当前已知缺陷。
- **late chunking**：需要更强的长上下文 embedding 和训练支持，当前栈不适合。
- **布局感知切块**：需要保留表格、图片和版面，目前文本侧无法做到。

## 6. Embedding 选型

### 6.1 当前选择

- 模型：Qwen3-Embedding-0.6B。
- 量化：Q8_0。
- 维度：1,024。
- 上下文：2,048 token。
- Pooling：last-token pooling。
- 部署：llama.cpp 的 `/v1/embeddings`。

query 和文档必须使用同一个 embedding 模型和同一个向量空间。换模型意味着整库重算。

### 6.2 为什么选 0.6B

在目标机器上要同时跑 embedding、reranker 和 9B generator，显存/统一内存有限。
0.6B 是成本和效果之间比较合适的点：

- 本地加载和重建成本可控；
- 中文语义和专有名词表现足够；
- 在当前 18 题上 Hit@5 已达 94%；
- 更大的模型不一定解决“专有名词精确匹配”和“图片缺失”问题。

当前瓶颈更像是 sparse 分支、数据质量和 query 表达，而不是 dense 模型容量。

### 6.3 未采用的方案和原因

| 方案 | 为什么暂不采用 |
| --- | --- |
| 更大的 Qwen3-Embedding 4B/8B | 内存、延迟和重建成本上升；当前 Hit@5 已较高 |
| OpenAI/云端 embedding | 破坏完全本地运行，增加成本和数据外发 |
| bge-m3 等替代模型 | 需要重新建库和完整 A/B，当前没有明显失败证据 |
| 领域 fine-tune embedding | 缺少高质量正负样本；先补数据和 hybrid 更划算 |
| Matryoshka 截断维度 | 当前 1,024 维和 1.7K 行不需要靠降维省空间 |
| sparse/SPLADE 向量 | 会引入新的模型和索引，优先用 trigram/BM25 做混合检索 |

### 6.4 一个重要实现差异

`docs/llama-cpp-stack.md` 记录了 Qwen3-Embedding 推荐的 query Instruct 前缀，
但当前 `src/lib/rag.mjs` 实际是把原问题直接送进 `/v1/embeddings`。

面试时不要把它说成已经实现。更准确的表述是：

> 模型卡建议 query 侧使用非对称 instruction 前缀，当前运行代码还没有拼。
> 这是一个低成本 A/B，应该先做离线评测再决定是否上线，不能凭经验直接改。

验证方式：固定同一份索引和 18/115 题，分别比较带前缀和不带前缀的 Hit@1、
Hit@5、MRR 和延迟；若提升不明显就不要增加 prompt 复杂度。

### 6.5 常见追问

- **为什么 query 和文档要同一模型？** 不同模型的空间不可比较，余弦相似度失效。
- **换模型后要做什么？** 全量重算 embedding，重建索引，重跑检索和答案评测。
- **需要归一化向量吗？** pgvector 的 cosine 距离会处理方向；不要混用 dot/L2 语义。
- **为什么不 microservice 化 embedding？** 当前是单机单用户，进程隔离已经足够。

## 7. 向量索引与存储

### 7.1 当前实现

表 `wiki_chunks` 同时保存文本、元数据和向量：

- `embedding vector(1024)`；
- HNSW + `vector_cosine_ops`；
- `(doc_type, source_id)` 复合索引；
- `metadata` GIN 索引；
- `chunk_key` 主键。

查询形式：

```sql
select ...
from wiki_chunks
where embedding is not null
  and token_count >= $3
order by embedding <=> $1::vector
limit $2;
```

### 7.2 为什么用 pgvector

1. 当前只需要单语料、单机、低并发。
2. 文本、元数据、向量和评测统计可以放在一个数据库里。
3. 事务、备份、SQL 过滤和运维工具都现成。
4. 1,718 行的规模不需要专门的向量数据库。

### 7.3 关于 HNSW 的准确说法

索引已经建好，但小表上 PostgreSQL 可能仍然选择顺序扫描。不要说“没有 HNSW 就跑不动”：

- HNSW 是近似最近邻索引，适合规模增长和低延迟 top-k；
- 当前数据量下，精确扫描也可能很快；
- 索引参数（`m`、`ef_construction`、`ef_search`）没有针对当前数据调优；
- 如果规模到十万/百万级，需要用真实 query 分布测召回率和 P95。

### 7.4 为什么不用专用向量数据库

- Qdrant、Milvus、Weaviate 会引入额外服务和运维复杂度；
- 当前没有多租户、分布式、十亿向量或高并发需求；
- PostgreSQL 已经承载元数据和评测结果，减少系统数量更重要。

### 7.5 未采用的索引方案

| 方案 | 当前判断 |
| --- | --- |
| IVFFlat | 需要训练/聚类参数；小规模收益不明显 |
| DiskANN | 面向大规模磁盘索引，当前规模过度设计 |
| 量化索引 / PQ | 省内存，但可能损伤召回；先测量再引入 |
| 内存暴力检索 | 小规模可用，但不方便扩展和持久化 |
| 多副本/分片 | 当前单机单语料不必要 |

### 7.6 入库一致性

当前 `ingest.mjs` 是并发 upsert，不是原子重建：

- 单块失败会汇总后报错；
- 不是“全部成功才切换”的 staging + swap；
- 全量重建期间查询可能看到旧数据或部分更新。

生产化应使用临时表/版本列，完成校验后原子切换，或至少做双写和回滚。

## 8. 在线检索与上下文组装

### 8.1 流程

1. 对问题做 embedding。
2. 按余弦距离召回 20 个 `token_count >= 60` 的块。
3. 如果开启精排，对 20 个候选调用 `/v1/rerank`。
4. 按排序依次取块，直到达到 `TOP_N=4` 或 `CONTEXT_BUDGET=2400`。
5. 拼接带编号的 context，生成回答。

### 8.2 为什么是 top 20 → top 4

- 20 是召回和精排成本的折中；
- 4 是事实问答的上下文预算折中；
- 如果只取 top 1，任何排序错误都会直接导致答错；
- 如果取太多，噪音和 token 成本都会上升。

这不是理论最优值，应该在验证集上做网格搜索。

### 8.3 当前没有做的上下文优化

- 没有按分数阈值截断，只按固定 top-N 和 token 预算。
- 没有每文档上限，top 4 可能来自同一篇机制的多个片段。
- 没有 MMR 去重。
- 没有相邻块扩展或 parent-doc 回填。
- 没有 context compression。

因此当前“检索到了”不等于“上下文最优”。

### 8.4 一个容易被追问的细节

快速模式没有真实余弦分数进入 UI。`rag.mjs` 用
`1 - index / rows.length` 生成一个名次代理分数。它适合展示排序，但**不能解释为
模型置信度或余弦相似度**。面试时如果被问“来源卡片上的分数是什么”，要如实回答。

## 9. 混合检索：本项目没有做

### 9.1 当前状态

当前只有 dense retrieval。曾经建过 trigram 索引，但实测 `idx_scan = 0`，
而且没有接入查询路径，所以后来移除。`pg_trgm` 不是当前运行依赖。

### 9.2 dense 和 sparse 的互补

| 方式 | 擅长 | 弱点 |
| --- | --- | --- |
| Dense | 语义改写、近义表达、跨措辞匹配 | 专有名词、数字、罕见词可能排后 |
| BM25/trigram | 精确词、实体名、数字、标题 | 不理解同义表达，容易受分词影响 |

这个语料专有名词很多，混合检索有明确价值。已知失败例：

- 问题“林肯法球能抵挡哪些技能？”中，相关文档在纯向量里只排到第 14，
  最终靠精排救回。
- 口语“魔晶升级”和语料字段 `shard_description` 不对齐时，dense 也会失手。

### 9.3 可选实现

```text
dense top 20
   +
sparse top 20（BM25 或 pg_trgm）
   ↓
按文档/块去重
   ↓
RRF 融合
   ↓
可选精排
```

RRF 的常见形式：

```text
score(d) = 1 / (k + rank_dense(d)) + 1 / (k + rank_sparse(d))
```

`k` 常取 60。它不要求两支分数同分布，适合本次场景。

### 9.4 为什么本项目没做

1. 18 题上 dense Hit@5 已达 94%，先做混合的收益没有被量化。
2. 小语料下 trigram 索引维护和查询复杂度不一定划算。
3. 评测集太小，容易为了单个失败例过拟合。
4. 当前更明显的瓶颈还包括重复块、无阈值、无邻居扩展和图片缺失。

### 9.5 什么时候应该做

如果出现以下任一情况，就应该把 hybrid 提上优先级：

- 专有名词/装备名问题的 Hit@1 明显低于语义问题；
- dense top 20 经常召回不到金标；
- 语料规模增长、同义词覆盖变差；
- 线上日志显示大量 exact-name query。

验收标准：

- 18 题 Hit@1/Hit@5/MRR 不下降；
- 专有名词子集明显提升；
- 增加延迟在预算内；
- 不破坏现有过滤和重排链路。

## 10. 重排序与 Reranker

### 10.1 概念区分

“重排序”是一个阶段，“reranker”是这个阶段采用的一种模型。

- 重排序可以是规则、分数融合、RRF、MMR、cross-encoder 或 LLM judge。
- 本项目的 reranker 是 Qwen3-Reranker-0.6B 交叉编码器。

### 10.2 Bi-encoder 与 cross-encoder

| 类型 | 工作方式 | 优点 | 缺点 |
| --- | --- | --- | --- |
| Bi-encoder | query 和 document 分别编码，再算相似度 | 可预计算、召回快 | query-doc 交互弱 |
| Cross-encoder | query 和 document 拼接后联合打分 | 精度高、能理解细粒度关系 | 每个候选都要跑一次，慢 |

常见两阶段：

1. bi-encoder 从全库召回 top-k；
2. cross-encoder 只对 k 个候选精排。

### 10.3 本项目实现

- 模型：Qwen3-Reranker-0.6B-Q6_K。
- 接口：`/v1/rerank`。
- 启动：`--reranking --pooling rank --embedding`。
- 候选：20。
- 输入：问题和候选块原文。
- 输出：相关分数，按降序返回。

### 10.4 效果与代价

| 指标 | 纯向量 | + 重排 |
| --- | --- | --- |
| Hit@1 | 83% | 94% |
| Hit@5 | 94% | 100% |
| MRR | 此处未记录 | 0.972 |

但在这台 M1 上，20 个候选约 13K token，重排要 20–50 秒。网页因此默认关闭：

- 快速模式：来源约 0.5s 出现，总耗时 20–40s；
- 精排模式：来源约 34s 出现，总耗时约 78s。

这不是“reranker 没价值”，而是“在当前硬件和交互目标下，默认不值得”。

### 10.5 为什么没有默认开启或换更大模型

- 9B 生成已经受内存带宽限制，约 10 token/s；
- 更大 reranker 会进一步拉长交互延迟；
- 当前 0.6B 已把 Hit@1 从 83% 提到 94%；
- 先优化候选筛选、阈值和每文档上限，可能比换更大 reranker 更划算。

### 10.6 未采用的 reranking 方案

| 方案 | 当前判断 |
| --- | --- |
| 永远开启 cross-encoder | M1 上交互不可接受 |
| 更大 reranker | 收益未验证，成本明显上升 |
| 领域 fine-tune reranker | 缺少标注对，优先补评测 |
| LLM-as-reranker | 更慢、更贵、不可控 |
| ColBERT/late interaction | 需要额外索引和训练，当前栈不匹配 |
| 规则加权 | 可作为 fallback，但无法替代语义精排 |

### 10.7 一个工程坑

Qwen3-Reranker 的 GGUF 必须包含 reranker 分类头、pooling 类型和 chat template。
社区里一些 naive 转换的 GGUF 能启动、能返回，但分数可能完全反了。正确配置下，
正确文档接近 1.0，无关文档接近 0；错误配置会出现无关文档 0.8、正确文档接近 0。

这也是面试可讲的点：**接口返回 200 不等于模型语义正确，必须做排序级别的验收。**

## 11. 生成与引用

### 11.1 当前生成配置

- Qwen3.5-9B-Q4_K_M；
- `temperature: 0.3`；
- `max_tokens: 600`；
- `enable_thinking: false`；
- SSE 增量输出；
- 只依据 context 回答；
- 资料不足时明确说“资料中没有提到”；
- 回答句末标 `[1]`、`[2]`。

关闭 thinking 是必要的：Qwen3.5 默认思考会消耗大量 token，正文可能迟迟不出现。

### 11.2 防幻觉做了什么

- prompt 明确禁止补充资料外知识；
- 低温度；
- 强制拒答话术；
- 来源编号；
- 答案评测中做数字支持检查。

### 11.3 防幻觉还缺什么

- 没有 claim-level citation verification；
- 没有检查每个引用编号是否真的支持对应句子；
- 数字检查只是子串启发式，可能误报；
- 没有 LLM judge 或 entailment 模型；
- 没有对用户问题做 prompt injection 隔离。

所以当前只能叫“降低幻觉”，不能叫“消除幻觉”。

## 12. 评测体系

### 12.1 两层评测

| 脚本 | 数据 | 作用 |
| --- | --- | --- |
| `npm run eval` | 18 道手写问题 | 检索排序质量 |
| `npm run eval:answer` | 115 条生成题 | 端到端答案质量 |
| `npm run gen:eval` | 从数据生成 | 构造有金标约束的题 |

### 12.2 检索指标

- **Hit@k**：top-k 中是否出现至少一个期望文档。
- **MRR**：第一个相关结果排名的倒数，未命中记 0。

当前 Hit@k 是按 `doc_type + title 正则` 判定，不要求所有相关文档都召回。

### 12.3 答案指标

- **context recall**：金标块是否进入最终 picked context。
- **MRR**：金标块在重排列表中的位置。
- **answer correctness**：归一化后的标准答案是否是回答的子串。
- **citation hit**：回答引用的块里是否至少有一个金标块。
- **abstain**：OOD 题是否出现拒答表达。
- **bad numbers**：回答中的数字是否能被 context 支持。

这些指标都可解释、成本低，但不是严格的语义评测。

### 12.4 评测集怎么构造

`gen-eval.mjs` 从英雄、技能、机制数据自动生成：

- 施法数值；
- 技能特殊数值；
- 技能归属；
- 机制概念；
- 5 条语料外问题。

关键约束：标准答案必须能在金标块里逐字找到，否则丢弃。这避免造出语料中没有的题。
金标使用 `(doc_type, source_id) + 答案原文`，而不是只绑定 `chunk_key`，
这样重切后不会静默失效。

### 12.5 评测的局限

- 18 题太少，单题变化就会造成很大的百分比波动。
- 自动生成题偏重短答案和数值，不能覆盖复杂多跳问题。
- 子串匹配会漏掉语义等价表达，也可能被模板化回答“骗过”。
- citation hit 只检查“是否引用到金标”，不检查引用是否支持结论。
- 数字检查是启发式，不处理单位换算、四舍五入和否定。
- 没有延迟、成本、拒答率的联合门槛。

### 12.6 面试时怎么证明“有效”

不要只说“我试了效果不错”。按以下顺序说：

1. 定义任务和指标；
2. 构造带金标的题；
3. 固定数据、模型和参数；
4. 对比 dense 与 dense+rerank；
5. 报告质量与延迟；
6. 说明评测集局限；
7. 给出下一步实验。

## 13. 失败案例与根因

| 现象 | 根因 | 当前处理 | 更好的下一步 |
| --- | --- | --- | --- |
| “林肯法球”相关文档向量只排第 14 | 专有名词精确匹配弱 | 精排救回 | hybrid + RRF |
| “魔晶升级”与 `shard_description` 不对齐 | 用户词表与语料词表不一致 | 依赖向量语义 | 查询改写/标签同义归一 |
| 17 篇机制文只有“请查询 X” | 上游站内跳转桩 | 跳过索引，名字写成目标页别名 | 保持，继续校验跳转 |
| 护甲公式答不出来 | 公式在 PNG 里 | 只给定性结论 | OCR/VLM |

| top-4 混入噪音块 | 固定 top-N，无阈值 | 精排可缓解 | 分数阈值 + 自适应 top-k |
| 命中第 5 块却缺第 4、6 块 | 小块检索、小块喂模型 | 无 | 相邻块扩展/parent-doc |

| 重建期间查询受影响 | 入库非原子、embedding 串行 | 单机人工避开 | staging + swap，构建查询隔离 |
| 英文术语/数字偶发不稳 | 分词、专名、dense 偏语义 | 精排部分缓解 | BM25/trigram 分支 |

## 14. 没有采用的 RAG 能力总表

先澄清：用户点名的七项里，文档解析、chunking、embedding、向量索引、重排序和
reranker 在本项目中都有实际实现；真正没有做的是**原始文档解析、chunking 的多种高级变体、
混合检索，以及一批上下文和评测增强**。下面逐项说明。

| 能力 | 状态 | 为什么没有采用 / 当前判断 | 触发条件 |
| --- | --- | --- | --- |
| 原始 HTML/PDF 解析 | 不在仓库 | 上游已归一化为 JSON；重复解析增加漂移 | 要接入新数据源或网页结构变化 |
| 布局感知解析/表格抽取 | 未做 | 当前文本侧已够用；表格主要在上游转 Markdown | 出现大量表格问答失败 |
| OCR/VLM 图片理解 | 未做 | 需要额外模型和存储；当前 16 GB 机器资源紧 | 公式、流程图类问题成为主要失败 |
| 固定长度 chunk | 未做 | 会切断实体和标题语义 | 语料变成无结构长文 |
| overlap chunk | 未做 | 当前按实体/标题切，重叠会增加重复召回 | 边界丢失成为主要问题 |
| 语义切块 | 未做 | 多一次 embedding，标题边界已足够 | 文档没有清晰标题结构 |
| parent-child retrieval | 未做 | 需要额外父子索引和回填逻辑 | 小块命中但上下文不完整 |
| 相邻块扩展 | 未做 | 当前直接喂小块；已知机制文会丢上下文 | 多跳/长机制题增多 |
| 更大 embedding | 未做 | 内存、延迟和重建成本高；当前 Hit@5 已高 | dense 召回成为主要瓶颈 |
| 领域 fine-tune embedding | 未做 | 缺正负样本；先补 hybrid 和数据质量 | 有稳定标注和明确收益 |
| sparse/SPLADE 向量 | 未做 | 引入新模型和索引；先用 BM25/trigram 验证 | dense 对专名/数字持续失败 |
| IVFFlat/DiskANN/PQ | 未做 | 当前 1.7K 行不需要 | 数据量或内存压力显著增长 |
| 专用向量数据库 | 未做 | PostgreSQL 已覆盖需求，少一个系统 | 多租户、高并发、分布式或十亿级 |
| metadata 过滤 | 索引已建、查询未用 | 当前问题没有稳定的实体过滤字段 | 增加英雄/版本/文档类型筛选 |
| 混合检索 BM25/trigram | 未做 | dense 在当前小评测上已较强；trigram 曾 0 扫描 | 专有名词子集 Hit@1 明显偏低 |
| RRF 融合 | 未做 | 依赖混合检索分支 | 接入 sparse 后 |
| 查询改写/同义归一 | 未做 | 需要词表或 LLM，增加延迟和不确定性 | 口语问题、别名问题增多 |
| HyDE | 未做 | 多一次生成，可能引入假前提 | 短 query 语义不足且可接受额外延迟 |
| 多查询/multi-query | 未做 | 成本和延迟成倍增加 | 复杂问题召回不足 |
| MMR/多样性 | 未做 | 当前 top-4 可能重复同文档 | 重复块占比影响答案 |
| 分数阈值 | 未做 | 固定 top-N 简单，但会混入噪音 | 有可靠的精排分数分布 |
| 自适应 top-k | 未做 | 需要校准和失败回退策略 | 问题难度差异大 |
| reranker 常开 | 未做 | M1 上 20–50 秒，交互不可接受 | 硬件升级或异步问答 |
| 更大/fine-tune reranker | 未做 | 收益未验证，成本高 | 精排成为质量瓶颈 |
| LLM-as-reranker | 未做 | 更慢、更贵、稳定性差 | 需要复杂相关性判断 |
| ColBERT/late interaction | 未做 | 需要专门索引和训练 | 大规模高质量检索需求 |
| 精确/语义查询缓存 | 未做 | 当前单用户、重复率未知 | 有真实流量和重复问题 |
| GraphRAG | 未做 | 已有标签和外键，LLM 抽实体性价比低 | 多跳关系成为主要需求 |
| 多 KB 隔离 | 未做 | 单语料，表结构没有 `kb_id` | 接入第二个数据源 |
| Agentic RAG | 未做 | 闭域事实问答，延迟和不确定性不划算 | 需要工具调用/多步规划 |
| 引用 entailment 校验 | 未做 | 需要额外模型或 LLM judge | 引用错误影响用户信任 |
| context compression | 未做 | 当前 2,400 token 预算还可控 | 上下文变长、成本上升 |
| LLM judge 评测 | 未做 | 成本高、可重复性差；先做严格金标 | 子串指标明显不够 |
| 生成模型 fine-tune | 未做 | 知识更新和引用需求优先 RAG | 需要固定风格/格式 |
| 生产级鉴权/限流 | 未做 | 当前只监听回环地址，单用户 | 对外提供服务 |
| 原子重建/零停机 | 未做 | 单机实验可接受 | 需要持续在线更新 |

### 14.1 为什么这个项目选择“窄而深”

原因不是“做不了”，而是当前资源和任务边界下：

- 语料只有约 1,100 个实体，先把 dense + chunking + eval 做扎实；
- M1 16 GB 内存同时承载三个模型，精排和生成已经是瓶颈；
- 没有真实线上流量，无法证明复杂 pipeline 的收益；
- 面试项目更重要的是能解释取舍，而不是堆功能名。

## 15. 高频面试问答

### Q1：为什么不直接 fine-tune 一个 Dota 模型？

知识更新、来源追溯和语料外拒答是核心需求，RAG 更合适。fine-tune 适合固定输出格式、
领域语言风格或让模型学会“如何使用检索结果”，不适合把快速变化的 wiki 当参数记住。

### Q2：为什么 chunk 不按 512 token 切？

这个语料有清晰的实体和标题边界。512 token 会把技能数值、描述和机制说明拆开，
造成上下文丢失；而 1,000 左右能保留一个语义单元。最终大小由评测和模型上限共同决定，
不是拍脑袋。

### Q3：为什么 chunk 重叠没有做？

按实体和标题切分后，重叠主要会增加重复召回和上下文冗余。重叠适合无结构长文或
边界不清晰的数据。当前更大的问题是相邻块扩展和每文档上限，不是 overlap。

### Q4：为什么 embedding 选 0.6B？

本地资源、延迟和效果折中。当前 18 题 Hit@5 94%，说明 dense 已经能覆盖大部分语义召回；
更大的模型不一定解决专有名词和图片缺失。先用 hybrid 和数据补丁解决明确失败更划算。

### Q5：为什么用 pgvector，不用 Milvus/Qdrant？

单机、单语料、约 1.7K 块，PostgreSQL 已经能同时承载文本、元数据和向量。少一个服务
就少一套备份、监控和故障模式。规模增长或需要分布式时再换。

### Q6：HNSW 是近似检索，怎么保证准确率？

用真实 query 测 top-k 召回和最终答案质量，而不是只看索引是否存在。当前数据量小，
即使 planner 选择顺序扫描也能接受；HNSW 是为增长预留的。规模变大后需要调
`ef_search` 并测 recall-latency 曲线。

### Q7：为什么只用 dense？

因为当前 dense 在小评测上已经足够，混合检索需要额外的索引、融合和评测。已知专名
失败例说明 hybrid 有价值，但应该先建立错误分组和验收标准，避免为了一个例子引入
整套复杂度。

### Q8：Reranker 为什么有效？

Bi-encoder 分别编码 query 和 document，交互能力有限；cross-encoder 把两者拼接后
联合判断，能识别更细的相关性。它只处理 20 个候选，所以适合作为第二阶段。

### Q9：为什么 reranker 默认关闭？

在 M1 上 20 个候选需要 20–50 秒，交互体验不可接受。质量提升是真实的，但产品默认
选择快速模式，把精排作为可选质量模式。

### Q10：怎么防止模型胡说？

四层：context-only prompt、低温度、资料不足拒答、来源编号；评测里再做数字支持检查。
但要诚实说明，引用还没有逐句 entailment 验证，所以只能降低风险，不能保证零幻觉。

### Q11：怎么评测 RAG？

分两层：

- 检索：Hit@k、MRR、context recall；
- 答案：正确性、引用命中、拒答、数字支持。

再补延迟和成本。当前评测集自动生成、金标有逐字约束，但仍不是人工 benchmark。

### Q12：最大的失败模式是什么？

不是“模型不够大”，而是：

1. 专有名词和数字的精确匹配弱；
2. 固定 top-4 混入噪音或重复文档；
3. 小块命中但缺少相邻上下文；
4. 图片/公式不在文本索引；
5. 上游数据本身有缺陷。

这些问题分别对应 hybrid、阈值/多样性、邻居扩展、OCR/VLM 和数据补丁。

### Q13：如果给你 10 倍数据量，先改什么？

先做数据版本化和 staging + swap，再做 hybrid、分片/索引参数调优和查询缓存。
同时把评测集扩展到按类型分层的几百题，否则无法判断系统是否真的退化。

### Q14：如果面试官问“你怎么知道不是 reranker 过拟合”？

当前 18 题确实太小，存在过拟合风险。正确回答是承认局限，并给出验证方案：
按问题类型分层、留出集、重复采样、置信区间、不同随机种子和人工盲评。

### Q15：为什么没有用 LangChain/LlamaIndex？

链路很短，自己写能清楚控制 SQL、token 预算、降级和错误处理。框架适合快速接很多
数据源，但也会隐藏关键细节。这个项目更重视可解释性和可调试性。

### Q16：如果 query 是“7.41 版本胜率最高的英雄是谁”？

这是语料外或实时数据问题。检索可能仍然返回一些英雄/机制块，但 prompt 要求只依据
资料回答，所以正确行为是拒答，而不是编造胜率。OOD 题专门测这个行为。

### Q17：这套系统能上线吗？

不能直接上线。缺鉴权、限流、持续在线重建、原子索引切换、引用校验、监控和
多用户并发压测。它适合作为可解释的本地原型和面试项目。

### Q18：下一步最值得做的三个实验？

1. query Instruct 前缀 A/B；
2. hybrid + RRF，按专有名词子集验收；
3. 每文档上限/分数阈值/相邻块扩展，优化 context 质量。

## 16. 推荐改进顺序

### P0：低成本、可量化

1. **query 前缀 A/B**
   - 不改索引；
   - 对比 Hit@1/Hit@5/MRR 和延迟；
   - 若收益不明显就保持简单。

2. **每文档上限**
   - 先限制 top-4 中同一 `(doc_type, source_id)` 最多 2 块；
   - 验收：去重文档数上升，Hit@1 不降。

3. **精排分数阈值**
   - 需要先收集分数分布；
   - 低于阈值不进入 context，至少保留 2 块；
   - 验收：噪音块下降，答案正确率不降。

### P1：解决明确失败

4. **hybrid + RRF**
   - dense top 20 + trigram/BM25 top 20；
   - 专名问题单独统计；
   - 验收：不牺牲语义题。

5. **相邻块扩展/parent-doc**
   - 先做 `source_id + chunk_index` 前后各 1 块；
   - 验收：多跳题完整度提升，context token 不超预算。

6. **引用校验**
   - 对 claim 和引用块做 entailment；
   - 验收：错误引用可量化并降级展示。

### P2：数据能力

7. **OCR/VLM**
   - 先补公式和流程图；
   - 验收：原先只能拒答的题能答出。

8. **查询改写/词表归一**
   - 用 973 个标签建立同义词和别名映射；
   - 验收：口语化 query 召回提升。

### P3：工程化

9. 查询缓存；
10. 原子重建和索引版本；
11. 分层评测集、CI；
12. 鉴权、限流、可观测性；
13. 多 KB 隔离。

## 19. 最后一页：面试官最想听到的三句话

1. **我能量化系统是否变好。** 检索和答案分开评测，指标和失败案例都能对上。
2. **我知道为什么不用更复杂的方案。** 混合检索、MMR、parent-doc、GraphRAG
   都有明确触发条件，而不是“不会做”。
3. **我能诚实说出当前边界。** 图片缺失、引用未校验、精排慢、评测集小，
   这些限制和下一步优先级都能讲清楚。
